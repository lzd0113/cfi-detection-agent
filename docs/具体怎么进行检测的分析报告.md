# CFI Agent 检测模式技术说明

## 概述

CFI Agent 支持 7 种检测模式，覆盖 5 个安全维度。所有模式均已并行化（ProcessPoolExecutor 多核处理），支持 ARM 32-bit Thumb 和 AArch64 双架构自动识别。

---

## 1. .so 级检测（detect_so_level）

**检测内容**：判断每个 .so 文件是否开启了 CFI。

**检测方法**：
1. 用 pyelftools 打开 .so 文件，读取 `.symtab` 或 `.dynsym` 符号表
2. 查找 `__cfi_check` 符号
3. 如果符号存在且 `st_value != 0` → CFI 已开启
4. 如果符号不存在或 `st_value == 0` → CFI 未开启

**原理**：`__cfi_check` 是 LLVM CFI 运行时的核心入口函数。开启 CFI 编译时，链接器会生成这个符号。它负责接收间接调用的类型哈希并做校验。如果这个符号存在且有定义，说明该 .so 参与了 CFI 跨 DSO 校验。

**速度**：最快，2953 个 .so 约 26 秒。因为只查符号不扫描指令。

**不包含**：不知道哪些函数受保护、调用点覆盖率等细节。

---

## 2. 函数级检测（detect_functions）

**检测内容**：将每个 .so 中的函数分类为受保护 / 基础设施 / 真正未保护。

**检测方法**：
1. 读取 `.symtab` 符号表，遍历所有 `STT_FUNC` 类型、`st_value != 0` 的符号
2. 按符号名分类：
   - 名字以 `.cfi` 结尾（如 `foo.cfi`）→ 去掉 `.cfi` 后缀，`foo` 标记为**受保护**
   - 名字以 `__cfi` 或 `.L.cfi` 开头 → 标记为**CFI 基础设施**
   - 其他 → 加入候选集
3. 从候选集中去掉已有 `.cfi` 版本的函数 → 剩下的就是**真正未保护**

**原理**：LLVM CFI 为每个需要保护的函数生成两个版本——`func.cfi`（含类型检查入口）和 `func`（原始函数体）。间接调用指向 `.cfi` 版本，经过 `__cfi_slowpath` 校验后跳转执行。有 `.cfi` 版本意味着该函数的间接调用受类型检查保护。

**为什么保护率低（2-7%）是正常的**：LLVM CFI 只为可能被间接调用的函数（导出函数、虚函数、函数指针引用的函数）生成 `.cfi` 版本。绝大多数内部函数只被直接调用（BL 指令），无法被劫持，不需要 `.cfi` 版本。

**还包含**：demangle 函数名（用 c++filt 批量转换 C++ mangled 名为可读名），统计保护函数数 / 未保护函数数 / 基础设施符号数。

---

## 3. vcall 检测（detect_vcall）

**检测内容**：虚函数调用（virtual call）的 CFI 覆盖率。

**检测方法**：
1. **找 slowpath 调用点**：扫描 `.text` 段，找到所有调用 `__cfi_slowpath` 的 BL/BLX 指令位置，记录地址列表（已排序）
2. **找间接调用点**：扫描所有 BLR（AArch64）或 BLX Rn（Thumb）指令
3. **分类 vcall vs icall**：对每个 BLR/BLX，向后回溯基本块内的指令：
   - 如果 BLR 的寄存器来自 LDR 加载（从内存读函数指针）→ **vcall**（可能是虚表调用）
   - 如果 LDR 的基址寄存器是 X0（this 指针）或 X19-X28（callee-saved，可能持有 vtable 指针）→ 判定为 **vcall**
   - 如果 LDR 的基址来自 SP（栈）→ 判定为 **icall**
   - 无法判定时用启发式（LDR 在 BLR 前 20 字节内 → vcall）
4. **CFI 判定**：对每个 vcall 调用点，用二分查找检查排好序的 slowpath 列表中，该调用点前后 48 字节内是否有 slowpath 调用
   - 有 → 该 vcall **受 CFI 保护**
   - 无 → 该 vcall **未受保护**

**原理**：LLVM CFI 在虚函数调用前插入 `__cfi_slowpath` 调用，校验目标对象的 vtable 类型哈希。48 字节是编译器插入 slowpath 检查的典型代码窗口（约 12 条 AArch64 指令）。

**bisect 优化**：slowpath 调用列表天然有序（按地址递增），用二分查找定位，每个调用点只需检查 2 个候选元素，整体复杂度从 O(n×m) 降到 O(n×log m)。

**输出**：vcall 调用点总数、受保护数、未受保护数、覆盖率。

---

## 4. icall 检测（detect_icall）

**检测内容**：非虚函数间接调用（indirect call）的 CFI 覆盖率。

**检测方法**：与 vcall 检测完全相同的扫描流程，区别只在分类：
- vcall：BLR 寄存器来自 vtable 加载（LDR 基址为 X0 或 callee-saved 寄存器）
- icall：BLR 寄存器来自其他来源（栈、堆、全局变量等），即非虚函数的间接调用

**CFI 判定方式相同**：同样检查调用点前后 48 字节内有无 slowpath 调用。

**原理**：icall 包括回调函数调用、函数指针调用等。这些间接调用同样可被劫持，CFI 通过类型哈希校验防护。vcall 和 icall 的 CFI 检查机制完全相同，区别只在调用来源（vtable vs 其他）。

**输出**：icall 调用点总数、受保护数、未受保护数、覆盖率。

---

## 5. PAC 检测（detect_pac）

**检测内容**：返回地址签名/认证覆盖率（仅 AArch64）。

**检测方法**：
1. **属性检查（第一层）**：读取 `.note.gnu.property` 段，检查 `FEATURE_1_PAC` 标志位，判断编译时是否开启 PAC
2. **字节级扫描（第二层）**：扫描所有可执行段，统计 HINT 指令中的 PAC 签名指令（PACIASP/PACIBSP，imm7=25/27）和认证指令（AUTIASP/AUTIBSP，imm7=29/31）以及 RETAA/RETAB 字节匹配
3. **函数级扫描（第三层）**：遍历 `.symtab` 中每个函数，在其地址范围内扫描：
   - 有签名指令（PACIASP/PACIBSP）+ 有认证指令（AUTIASP/AUTIBSP 或 RETAA/RETAB）→ **protected**（有效防护 ROP）
   - 只有签名指令无认证 → **sign_only**（签名无效，等于没保护）
   - 两者都没有 → **no_pac**（无 ROP 防护）

**原理**：
- PACIASP/PACIBSP 在函数入口签名返回地址（LR），用密钥计算 PAC 码插入指针高位
- AUTIASP/AUTIBSP 在函数返回前验证 PAC，不匹配则触发异常
- RETAA/RETAB 是"认证+返回"的组合指令
- 只有签名没有认证，攻击者可以忽略签名直接返回，等于没有防护

**32 位跳过**：PAC 是 ARMv8.3-A 专属特性，32 位 ARM 不支持。检测前抽样检查架构，全是 32 位直接返回"不适用"。

**输出**：PAC 签名指令数、认证指令数、函数级分类（protected/sign_only/no_pac）、覆盖率。

---

## 6. BTI 检测（detect_bti）

**检测内容**：函数入口 BTI 指令覆盖率（仅 AArch64）。

**检测方法**：
1. **属性检查（第一层）**：读取 `.note.gnu.property` 段，检查 `FEATURE_1_BTI` 标志位
2. **函数入口扫描**：遍历 `.symtab` 中每个函数，检查其入口地址的首条指令：
   - 是 BTI 指令（HINT imm7 = 32/34/36/38）→ **有 BTI**
   - 不是 BTI 指令 → **无 BTI**

**原理**：
- BTI（Branch Target Identification）是 ARMv8.5-A 特性
- 内核根据 `.note.gnu.property` 的 `FEATURE_1_BTI` 标志决定是否对该进程启用 BTI 强制
- 启用后，间接跳转（BR/BLR）到非 BTI 指令地址会触发异常
- 编译器在函数入口插入 BTI 指令，使其成为合法的间接跳转目标
- BTI 指令类型：BTI（通用）、BTI c（仅 call）、BTI j（仅 jump）、BTI jc（call+jump）

**防护攻击**：JOP（Jump-Oriented Programming）——攻击者无法跳转到函数中间的 gadget，因为目标地址没有 BTI 指令会触发异常。

**32 位跳过**：同 PAC，BTI 也是 AArch64 专属。32 位 ARM 不支持。

**输出**：BTI 指令总数、有 BTI 函数数、无 BTI 函数数、覆盖率。

---

## 7. 完整检测（run_cfi_detection）

**检测内容**：上述全部 5 个维度一次性检测。

**检测流程**（每个 .so 并行处理）：
1. 打开 ELF 文件
2. 检查 CFI 是否开启（`.so` 级）
3. 分类函数（函数级）
4. 如果 CFI 开启：扫描 vcall + icall 调用点
5. 如果是 AArch64：扫描 PAC + BTI
6. 汇总所有结果

**后续步骤**（串行）：
1. demangle 所有函数名（c++filt 批量）
2. 按模块聚合统计
3. 生成 SQLite 数据库（6 表 7 索引，先插数据后建索引）
4. 生成 HTML 报告（ECharts 可视化）
5. 生成 Excel 报告（4 Sheet）
6. 生成 Flask API + data.js + .pyw 启动器

**速度**：2953 个 .so 约 2 分钟（并行），其中检测约 1.5 分钟，报告生成约 30 秒。

## 检测维度对照表

| 维度 | 防护的攻击 | 关键检测方法 | 架构 |
|------|-----------|-------------|------|
| .so 级 | 整体安全基线 | 查 `__cfi_check` 符号 | 32位+64位 |
| 函数级 | vtable hijacking / 间接调用劫持 | 查 `.cfi` 后缀符号 | 32位+64位 |
| vcall | 虚函数调用劫持 | BLR 扫描 + 寄存器回溯 + slowpath 判定 | 32位+64位 |
| icall | 间接调用劫持 | 同 vcall，分类不同 | 32位+64位 |
| PAC | ROP（返回地址篡改） | HINT 指令扫描 + 函数级 sign/auth 分类 | 仅 AArch64 |
| BTI | JOP（跳转劫持） | 函数入口 BTI 指令检查 | 仅 AArch64 |

## 三种安全特性协同关系

| 特性 | 方向 | 防护 | 机制 |
|------|------|------|------|
| LLVM CFI | 前向（间接调用） | vtable hijacking、间接调用劫持 | 类型哈希 + slowpath 校验 |
| BTI | 前向（间接跳转目标） | JOP | 函数入口 BTI 指令 |
| PAC | 后向（返回地址） | ROP | 返回地址签名 + 认证 |

三者互补：CFI 防间接调用、BTI 防间接跳转、PAC 防返回地址。完整防护需要三者同时开启。
