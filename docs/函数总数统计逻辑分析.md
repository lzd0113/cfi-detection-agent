检测逻辑分析：函数总数统计口径与静态链接问题
================================================

一、问题背景
----------

对 OpenHarmony .so 文件进行 CFI/PAC/BTI 检测时，发现同一个 .so 存在两个
不同的"函数总数"：

  - CFI 函数总数：classify_functions() 统计的 protected + unprotected
  - PAC/BTI 函数总数：_scan_pac_bti_functions() 统计的全部 STT_FUNC

两者不一致，用户质疑哪个正确，以及统计逻辑是否存在矛盾。


二、.symtab 中的 STT_FUNC 符号分类
---------------------------------

一个 .so 的 .symtab 中，STT_FUNC 类型符号分三种：

  1. 本 .so 定义的函数
     - st_value != 0（指向本 .so 内的代码地址）
     - 代码在本 .so 的 .text 段中
     - 包含：本 .so 原生函数 + 静态链接进来的第三方函数
     - 细分：
       a. 普通函数（如 foo）
       b. .cfi 后缀函数（如 foo.cfi，LLVM 生成的 CFI 插桩入口）
       c. __cfi* 基础设施函数（如 __cfi_check、__cfi_check_fail）
     - 数量举例：155 个普通 + 1 个 .cfi + 2 个 __cfi* = 158 个

  2. 外部引用函数（动态链接）
     - st_value == 0（未定义，指向空地址）
     - 代码在其他 .so 中（如 libc.so）
     - 例如：malloc、free、memcpy、abort、pthread_rwlock_* 等
     - 数量举例：43 个

  3. 无名函数
     - name 为空字符串
     - CFI 和 PAC/BTI 都跳过（无法按名称分类）


三、两种检测的统计口径
---------------------

CFI 函数分类（classify_functions）：
  - 统计范围：st_value != 0 且 name 非空的 STT_FUNC
  - 分类方式：按 .cfi 后缀分类
    - 有 .cfi 后缀 → CFI 保护函数（按基名去重，foo.cfi 算作 "foo"）
    - __cfi* / .L.cfi* → CFI 基础设施函数
    - 其他 → CFI 未保护函数
  - 使用 set 去重，同名函数只计一次
  - Excel 显示的"函数总数" = protected_count + unprotected_count
  - 不含 .cfi 后缀函数和 __cfi* 基础设施函数
  - 修复前 bug：未过滤 st_value==0 的外部符号，导致总数虚高

PAC/BTI 函数分析（_scan_pac_bti_functions）：
  - 统计范围：st_value != 0 且 name 非空 且不以 .cfi 结尾的 STT_FUNC
  - 跳过 .cfi 后缀函数：foo.cfi 和 foo 是同一个逻辑函数，只计 foo 一次
  - 按 (name, st_value) 去重，避免别名符号重复计数
  - 分类方式：
    - PAC：扫描每个函数的指令范围，找 PACIBSP（签名）+ AUTIBSP（认证）
    - BTI：检查每个函数入口首指令是否为 BTI
  - 统计范围包含 __cfi* 基础设施函数（它们也是本 .so 的真实函数）


四、为什么两个总数不同
---------------------

以 libace_network.z.so 为例：

  全部本 .so 定义的函数（st_value≠0, 有名字）：445 个
    ├─ .cfi 后缀函数：    15 个  ← 两个检测都跳过（foo.cfi 和 foo 是同一函数）
    ├─ __cfi* 基础设施：   2 个  ← CFI 归为 infra，PAC/BTI 计入总数
    └─ 其他函数：        443 个  ← CFI 的 protected(14) + unprotected(429)

  PAC/BTI 函数总数 = 445（含 __cfi*，不含 .cfi 后缀）
  CFI 函数总数     = 443（不含 .cfi 后缀和 __cfi*）
  差异 = 2（= __cfi* 基础设施函数数量）

  关系：PAC/BTI 函数总数 = CFI 函数总数 + CFI 基础设施函数数
       445              = 443           + 2

用户可直接从 Excel 验证：
  PAC函数总数（445）= 函数总数（443）+ CFI基础设施函数（2）
  PAC覆盖率 = PAC函数保护 / PAC函数总数 = 145 / 445 = 32.6%
  BTI覆盖率 = BTI函数覆盖 / BTI函数总数 = 4 / 445 = 0.9%


五、为什么 .cfi 后缀函数不计入 PAC/BTI 总数
------------------------------------------

LLVM CFI 编译时为每个受保护函数生成两个符号：
  - foo     — 原始函数体（有 PACIBSP/AUTIBSP 如果 PAC 已启用）
  - foo.cfi  — CFI 插桩入口（类型检查 + 跳转到 foo）

foo.cfi 和 foo 是同一个逻辑函数：
  - foo.cfi 只是 foo 的 CFI 插桩入口，不是独立的应用函数
  - 如果计入 foo.cfi，等于对同一个函数计数两次
  - foo.cfi 的 PAC 状态与 foo 相同（编译时一起生成）
  - 计入 foo.cfi 会虚高分母，导致 PAC 覆盖率虚低

从安全评估角度：
  - 覆盖率应反映"应用函数"的保护情况
  - foo.cfi 是编译器生成的跳板，不是应用函数入口
  - 跳过它使覆盖率更准确


六、为什么 st_value==0 的外部符号不应计入
--------------------------------------

外部符号（st_value==0）是定义在其他 .so 中的函数引用，例如：
  malloc、free、memcpy、abort、HiLogPrint、__cfi_slowpath、
  __ubsan_handle_*、pthread_rwlock_*、_Znwm (operator new) 等

不应计入的原因：

  1. 代码不在本 .so 中
     - 无法扫描其指令范围找 PACIBSP/AUTIBSP/BTI
     - 无法检查有没有 .cfi 后缀版本（.cfi 版本在定义该函数的 .so 里）

  2. CFI 是编译期机制
     - LLVM 在编译本 .so 时对本 .so 的函数生成 .cfi 插桩
     - 外部函数的 CFI 保护由定义它的 .so 负责（如 libc.so）
     - 在检测本 .so 时不应把外部引用当作本 .so 的未保护函数

  3. 重复计数问题
     - 如果本 .so 检测时把 malloc 计为"未保护函数"
     - 检测 libc.so 时也会把 malloc 计一次
     - 同一个函数被统计两次，导致总数虚高、保护率虚低

  4. 安全评估的边界
     - 每个函数由"包含其代码的 .so"负责评估
     - malloc 的代码在 libc.so → 在检测 libc.so 时评估
     - 本 .so 只评估"代码确实在本 .so 中的函数"


七、静态链接的情况
-----------------

静态链接是指：第三方库的函数体被编译进了本 .so，而不是运行时从其他 .so
动态加载。

例如：本 .so 静态链接了 memcpy，则：
  - .symtab 中 memcpy 的 st_value != 0（指向本 .so 内地址）
  - memcpy 的代码在本 .so 的 .text 段中
  - 可以扫描其指令找 PAC/BTI
  - 可以检查有没有 .cfi 后缀版本

与动态链接的区别：

                    动态链接              静态链接
  ─────────────────────────────────────────────────────────
  原始来源           其他库               其他库
  代码物理位置       在别的 .so 里        在本 .so 的 .text 里
  st_value           0                    非 0
  能否扫指令         不能                  能
  是否计入函数总数   不计入                计入

当前检测的过滤条件 st_value != 0 天然区分了这两种情况：
  - 静态链接函数 st_value != 0 → 计入，扫描指令
  - 动态链接函数 st_value == 0 → 跳过，不扫描


八、静态链接检测逻辑的合理性
---------------------------

有人质疑：动态链接不检测，静态链接检测，逻辑上是否矛盾？

不矛盾。检测的划分标准不是"函数是不是本 .so 自己的"，而是"代码物理上在不在
本 .so 里"：

  - 动态链接的 malloc：代码在 libc.so，不在本 .so → 本 .so 检测时跳过，
    在检测 libc.so 时会被评估
  - 静态链接的 memcpy：代码已编译进本 .so → 本 .so 检测时计入，
    因为这段代码确实在本 .so 中运行，攻击者可以通过本 .so 利用其漏洞

从安全评估角度：
  - 覆盖率评估的是"最终二进制文件中实际运行的代码有没有保护"
  - 静态链接的代码虽然来源是第三方，但它运行在本 .so 的进程空间
  - 如果它没有 PAC/BTI/CFI，这是本 .so 的真实安全缺陷
  - 覆盖率应该反映这个事实，不能因为"代码是第三方写的"就排除

从实际限制角度：
  - 从 .so 二进制本身无法区分"原生函数"和"静态链接的第三方函数"
  - 两者都是 st_value!=0、代码在 .text
  - 除非使用 DWARF debug info 中的编译单元信息，或按函数名模式匹配
  - 这些不在标准检测范围内


九、NO CFI .so 的函数统计
-------------------------

对于未开启 CFI 的 .so，仍然统计其函数：
  - classify_functions() 对所有 .so 都执行（无论 CFI 是否开启）
  - NO CFI .so 的所有函数都是"未保护"（没有 .cfi 后缀版本）
  - Excel 中显示：CFI保护函数=0，CFI未保护函数=实际函数数，函数总数=实际值
  - PAC/BTI 仍然检测（PAC/BTI 与 CFI 是独立的安全机制）


十、修复记录
-----------

修复 1：classify_functions() 过滤外部符号

  修复前：未过滤 st_value==0，外部符号（malloc 等）被计入函数总数
  修复后：if sym['st_value'] == 0: continue

修复 2：classify_functions() 去重

  修复前：other_funcs 是 list，同名符号重复添加
  修复后：other_funcs_set 是 set，同名函数只计一次

修复 3：_scan_pac_bti_functions() 去重

  修复前：func_syms 是 list，同一函数（同名同地址）重复计数
  修复后：按 (name, st_value) 去重

修复 4：_scan_pac_bti_functions() 跳过 .cfi 后缀函数

  修复前：foo.cfi 被当作独立函数计入 PAC/BTI 总数
  修复后：if s.name.endswith('.cfi'): continue
  原因：foo.cfi 和 foo 是同一逻辑函数，计入两次导致分母虚高

修复效果（以 libace_network.z.so 为例）：

  修复前：CFI 总数=443，PAC 总数=460（含 .cfi），差异=17（无法解释）
  修复后：CFI 总数=443，PAC 总数=445（不含 .cfi），差异=2（= __cfi* 基础设施）

  用户可验证：PAC 总数(445) = 函数总数(443) + CFI基础设施(2)


十一、三个检测维度的统计范围总结
-------------------------------

  检测维度              统计范围                              外部符号  .cfi后缀
  ────────────────────────────────────────────────────────────────────────────────
  CFI 函数级分类        st_value≠0 且有名字 且非 __cfi*        不包含    按基名计1个
  vcall/icall 调用点     扫描 .text 中所有 BLR 指令             不涉及    不涉及
  PAC/BTI 函数级        st_value≠0 且有名字 且非 .cfi 后缀     不包含    跳过

  共同点：都只处理"代码物理上在本 .so 中"的函数
  CFI 与 PAC/BTI 的差异：
    - CFI 不含 __cfi* 基础设施函数（归为 infra 单独统计）
    - PAC/BTI 含 __cfi* 基础设施函数（它们也是需要 PAC/BTI 保护的真实函数）
    - 两者都跳过 .cfi 后缀函数（foo.cfi 和 foo 是同一函数）
    - 关系：PAC/BTI 总数 = CFI 总数 + CFI 基础设施函数数
